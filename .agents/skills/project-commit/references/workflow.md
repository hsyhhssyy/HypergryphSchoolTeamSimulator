# 提交流程

## 1. 审计当前状态

在仓库根目录检查：

```bash
git status --short
git diff --stat
git diff
git diff --cached --stat
git diff --cached
```

同时查看近期提交标题以匹配仓库惯例：

```bash
git log -10 --pretty=format:%s
```

审计当前全部改动，理解每一项变更的目的，以便生成能够覆盖整个工作区的提交信息。不要判断改动由谁产生，也不要因为改动与当前对话任务无关而排除它。

## 2. 确认可提交性

- 检查是否存在未解决冲突、明显的敏感信息或其他会使提交本身不安全的状态。普通临时文件、生成物、用户改动或其他 Agent 改动不构成选择性提交的理由。
- 执行 `git diff --check` 检查空白错误。
- 复用当前已知的测试结果。除非用户同时要求验证，否则提交动作本身不自动扩大为修改代码或运行完整测试；未验证时在提交结果中如实说明。
- 若验证失败，报告失败并停止提交，除非用户明确要求提交当前已知失败的状态。

## 3. 保持整个工作区范围

项目提交脚本会暂存全部 tracked、untracked 和已有 staged 改动。用户要求提交当前项目时，这就是预期范围。

不得按作者、当前任务相关性或文件类型选择性暂存，也不得将工作区拆成“我的改动”和“其他改动”。只有用户明确指定提交部分文件或明确要求拆分提交时，才偏离全量提交；这种情况下不得使用 `commit-all.sh`。如果工作区没有改动，脚本会正常退出且不创建空提交。

## 4. 生成提交信息

遵循近期历史中占主导的 Conventional Commits 风格：

```text
<type>[(scope)]: <简洁的英文行为描述>
```

常用类型：

- `feat`：新增用户可感知能力。
- `fix`：修复错误行为。
- `test`：仅测试相关改动。
- `docs`：仅文档改动。
- `refactor`：不改变外部行为的结构调整。
- `chore`：工具、依赖或仓库维护。

标题应尽量概括整个工作区最主要的目的，不罗列文件名，不使用笼统的 `update files`。存在多项独立改动时仍创建一个提交，并选择能覆盖整体的标题；不要自行拆分。

## 5. 创建并核验提交

通过仓库统一入口提交：

```bash
./commit-all.sh "<message>"
```

不得直接调用 `git add` 或 `git commit` 绕过该脚本。脚本会检查冲突和空白错误、暂存整个工作区并创建 commit，但不会执行 `git push`。

提交后检查：

```bash
git status --short
git show --stat --oneline --decorate --no-renames HEAD
```

核验提交确实包含预期文件，并报告工作区是否仍有未提交改动。不得自动执行 `git push`。
